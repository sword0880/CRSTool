## 2. 范围与发布阻断规则

**产品正式名称：**“境外证券投资所得税辅助计算工具”（项目标识 CRS）；面向个人提供辅助计算与来源核对，不自动申报，不作唯一税务结论。初期公开版只支持已验证的 IBKR Activity Flex XML 和指定布局的富途 XLSX / 文本 PDF，以及文档列明的普通股票/ETF和部分现金、成本事件。

**以下情况不得声称已获得完整申报金额：**

- 期初 LOT 不真实/不完整，手续费或买卖成本未知，含不支持的公司行动/转仓/衍生品、无法证明 FIFO 顺序；
- 年度文件缺少账户/现金/交易覆盖、跨来源重复、无法核对券商金额；
- 汇率采用临时平均报价或法定折算/年度适用性未获确认；
- 所得来源国、分类、成本认定、**不同市场与证券类型股票转让的特别税制**、可抵免税及法定凭证尚待人工核验；
- 历史复算缺冻结规则/输入/执行证据，或税额状态标记不允许给出预计补税。

继续遵守既有四维状态：`CalculationStatus`、`DataCompleteness`、`ReconciliationStatus`、`UsageLabel`。`Summary.SupplementTax` 不得被 UI 或导出偷换成受门槛限制的 `EstimatedTopUpCny`。适用性验证以 `TAX_RULE_VALIDATION.md` 为准，证据链以 `CALCULATION_EVIDENCE_SPEC.md` 为准。

## 3. 发布包方案选型

### 3.1 优先建议：自包含文件夹发布（V1.0），正式版再确定安装器

**推荐 V1.0**：`win-x64`、Release、自包含（self-contained）文件夹发布。理由是无需先要求用户安装 .NET Desktop Runtime，便于核查 WPF、SQLCipher、NPOI、PdfPig 和原生依赖是否完整；自用阶段通过手动分发/升级更易控制。**不是已经验证的现成发布产物。**

**拟使用的验证命令（在项目根目录执行）：**

```powershell
dotnet restore CRS.sln --locked-mode
dotnet publish src/CRS.Desktop.Wpf/CRS.Desktop.Wpf.csproj `
  -c Release -r win-x64 --self-contained true `
  -p:PublishSingleFile=false `
  -o artifacts/publish/win-x64
```

- 上述命令需要以实际源码 `.csproj` 和包锁配置校验。发布包保留运行所需的配置/资源，不包含私人的 `crs.db`、`settings.json`、日志、报表、样本、密钥或任何真实券商文件。
- **暂不默认启用 `PublishSingleFile=true`、裁剪（trimming）或 Native AOT**。WPF/XAML、反射、动态资源及 SQLCipher 原生库在这些优化下需专门测试；“一个 EXE”不应优先于正确打包和故障诊断。
- `self-contained` 带来应用内置运行时的安全维护责任；.NET 运行时安全更新不会自动修补已经交付的独立包，须通过新版本重新发布。
- 初期以 `win-x64` 为发布基线。`win-arm64` 或 x86 只在确有需求且已验证所有依赖（特别是 SQLCipher 原生 DLL）后开放。

## 4. 版本与兼容治理

应当分别管理下面四种版本，绝不混淆：

| 版本类型 | 示例/来源 | 兼容性政策 |
| --- | --- | --- |
| 应用版本 | `AppVersion`，例如待分配的 `1.0.0` | SemVer 或明确版本规则；发行与实际构建绑定 |
| 税务规则版本 | 当前 `TaxEngine.PolicyVersion = V2-2026-10` | 必须冻结历史口径；规则变更新增版本，不静默改写旧结果 |
| 算法/证据格式 | `FIFO_TOTAL_COST_V3`、`CRS.CanonicalInput.v2`；拟增加 Evidence schema | 使用显式版本验证、固定测试向量；不因名称相近认定兼容 |
| 数据/保险库格式 | SQLite `user_version`、SQLCipher/Key Envelope/Vault Format | 只升级**已受支持的加密保险库**，加密格式与业务 schema 分开管理 |

### 4.1 明文数据库政策：固定决策、无例外

1. 新安全版遇到文件头 `SQLite format 3\0` 等明文库标识时，**拒绝打开和计算**。
2. **不提供**明文 SQLite → SQLCipher 转换、旧库导入或自动迁移选项；不因打不开库而新建覆盖同一路径。
3. 仅经用户明确操作在**新的空目录/不存在的目标文件**创建加密保险库。旧明文库及 `-wal`、`-shm` 保持原样，不自动删除/重命名。
4. 新库不会继承旧历史任务、人工复核、冻结结果。必要时用户重新导入原始富途/IBKR 报表并重新核对，不能保证自动还原全部旧业务状态。
5. 该拒绝规则必须进入启动测试、发布说明和数据隐私提示；安装器不得顺手删除既有用户资料。

### 4.2 加密库间的合法升级路径

**只允许**受支持的加密保险库 `schema N → schema N+1` 或明确支持的加密格式升级。流程应当是：

- 识别 Vault/Envelope/数据库 schema 版本并验证完整性、用户凭证及兼容性；
- 在已解锁状态下创建加密、一致性、可恢复的旧库备份；事先验证备份可以解密/恢复；
- 采用事务/临时目标及版本化迁移步骤，对已加密数据实施结构升级（必要时使用新加密临时库），**不留下明文数据库临时副本**；
- 失败时恢复旧加密保险库，输出脱敏错误；禁止失败后强制初始化或抛弃历史数据；
- 完成后校验业务金额、任务数量、历史版本、证据摘要及备份恢复；
- 用户更换电脑仅通过**加密备份恢复**，不绑定 Windows SID 或 DPAPI 作为唯一恢复条件。

**兼容矩阵由实际测试建立**：最低支持的旧加密 Vault 版本、是否需要分步升级、是否有可用回滚包，不得在实现前写成已兼容。旧 `CRS.CanonicalInput.v1`/旧结转 `Version=1` 不是自动兼容承诺；沿用 `AR-05` 门槛。

- 检查高 DPI（100/125/150/200%）、不同中文/英文 Windows 区域文化、UTC/本地时区、缺少 Internet、非管理员账户和受限目录。

### 6.2 必测故障场景

| 场景 | 必须结果 |
| --- | --- |
| 发现旧明文 `crs.db`（含 WAL/SHM） | 明确不支持；**不读、不迁、不删、不覆盖**；仅新空目录建库 |
| 密码错误/恢复密钥错误/加密库损坏 | 拒绝解锁；不回退普通 SQLite，不自动重建 |
| TOTP 未绑定/错误/被重放/并发消费 | 正常业务入口保持关闭；绑定必须首码确认；同一步原子消费仅一次成功 |
| 手机丢失/恢复码已使用/旧备份恢复 | 仅允许显式恢复流程；一次性恢复码不可重用，恢复后必须重新绑定；警告旧备份残留凭证 |
| 锁屏/休眠/超时与后台任务竞态 | 会话失效且写入/导出不能越权完成 |
| 保险库结构升级失败 | 原加密库和加密备份可恢复，原历史任务不丢失 |
| 源文件导入中被外部改写 | 输入摘要与解析使用同一不可变字节或显式失败 |
| 导出磁盘满/取消/同名目标存在 | 不留半成品文件，不静默覆盖原文件 |
| 完整快照缺失/旧版本重放 | 仅冻结查看或明确阻断，不假定用当前规则可重算 |
| 真实证券事件超出支持范围 | 显示准确问题代码及局部结果限制，不编造零金额 |
| 有抵免但缺有效凭证/来源国家未知 | 预计补税保持未知，不能宣传为已审核结果 |
| 压缩包损坏/签名失败/更新中断 | 拒绝不可信包；旧应用与已加密用户数据仍可使用 |

## 7. 签名、供应链和隐私发布要求

- **供应链**：使用受版本锁定的 NuGet 包；维护最终发布依赖 BOM（含原生 SQLCipher、许可证、哈希和出处）；对 CVE/不受维护依赖建立复查流程。包锁只限定版本，并不能单独证明安全。
- **许可证**：第三方商业使用、归属、源代码/NOTICE 分发义务需逐库审核；不得因为 GitHub 开源就假定所有依赖均为 MIT。正式决定项目自身许可证和免责声明。
- **签名**：为发行安装包/可执行文件按分发渠道进行可信签名；签名私钥不得存在 Git 仓库或打包产物中；发布清单保存包 SHA-256 和签名验证结果。
- **隐私**：默认本地离线；明确仅用户主动触发 IBKR Flex 下载时发出相应 HTTPS 请求；**不采集真实交易数据做遥测或故障上报**，除非另有单独知情同意和严格数据最小化设计。
- **客服/反馈**：只允许脱敏诊断包，禁止索取主密码、恢复密钥、完整税务报表；为用户提供本地删除/导出/备份说明以及公司受管终端风险提示。
- **安全说明**：加密保护静态数据，不宣称防护具有高权限的终端管理系统读取运行时已解密内容。
- **法律与业务表述**：所有产品描述统一为“辅助测算”，对未核验规则展示限制，不声称依法自动申报或保证税额准确。

## 8. 更新分发、回滚与用户数据政策

1. 应用二进制、用户数据库、密钥封装信息、配置/缓存和备份相互独立；更新包不携带个人数据。
2. 下载安装与文件完整性、签名核验由明确选定的发行机制实现；不得自动执行无法验签的更新。
3. 数据库结构/保险库格式变更前先验证解锁与加密一致性备份；失败时回滚结构或恢复旧备份。
4. **应用二进制回滚 ≠ 数据格式回滚**。发布前提供受支持版本的兼容矩阵；如果旧版不支持新保险库格式，应明确阻断而不能错误读取。
5. 旧版明文 SQLite 完全不纳入新安全版的数据升级路径。
6. 卸载默认**不自动删除用户个人保险库或备份**；若提供“清理个人数据”功能，须经二次确认并披露云同步/备份/SSD 残留不可保证物理擦除。
7. 对安全和计算错误准备撤回/下架版本、冻结自动更新、受影响版本标识、客户通知、恢复旧加密备份和重新计算的应急流程。

## 11. 与现有文档及 Work 并行实施的协作边界

| 文件 | 职责 | 本次与 Work 并行的注意事项 |
| --- | --- | --- |
| `SECURITY_DESIGN.md` | 密码、密钥、SQLCipher、锁定、备份、拒绝明文库 | **由 Work 的安全实施实际结果更新**，本文件不重复定义密码学接口 |

| `RELEASE_ACCEPTANCE.md` | 现有发布门禁及结果 | 只有在真实运行/验收后同步修改，不凭计划更改批准状态 |
