## 1. 目的与执行原则

本文件是后续专项整改的统一执行清单。每项整改必须先确认当前 main 是否已有后续修复，再决定实施，不得直接按历史评审描述盲目改代码。

总体判断：保留当前 WPF + Domain/Application/Infrastructure + Windows Service + Quartz.NET + SQLCipher 的技术路线。现有架构不需要全面推翻；优先消除模块所有权不清、旧机制残留、查询副作用和跨领域事实重复建设，并补齐数据恢复及发布验收。

执行原则：

1. 先读本文件、`docs/architecture/CURRENT_ARCHITECTURE.md`、`docs/KNOWN_ISSUES.md`、相关专项实施记录和当前源码。
2. 每个任务以小 PR/独立提交实施；先增加或更新回归测试，再改代码。
3. 先做不改变业务结果的结构整改；不得把架构重构与税务口径、ETF数据口径、预警阈值变更混在一个提交中。
4. 保持现有安全边界：私人税务/账户保险库与公共市场监控数据域不得因为“统一事实层”而合并数据库或密钥。
5. 任何“已修复”必须同时提供代码证据、测试证据和剩余限制；文档更新不等于实现完成。
6. 旧标识如 SCM 服务名、服务 SID、Named Pipe 名、数据目录、插件 ID/Job ID、DPAPI 附加熵和持久化字段均不得机械重命名。

## 2. 证据等级

| 等级 | 含义 | 文档表达 |
|---|---|---|
| S：源码确认 | 在评审基线的具体项目文件/方法中直接看到实现或依赖 | 可称“已确认的结构问题/设计限制”；仍需测试才能声称运行时后果已复现 |
| D：文档记录 | 当前架构、问题清单或验收记录明确记载 | 可称“记录为未完成/未通过”；执行前需核对最新记录 |
| H：待验证假设 | 从设计推导出的潜在风险，尚无直接证据证明当前已发生 | 只能列为验证项，不得称为已发生 Bug |
| V：验收结论 | 有可重复测试/实机结果和明确通过条件 | 仅对测试覆盖范围内的场景关闭问题 |

源码行号会随变更漂移。实施时以文件、类型和方法名定位，并在 PR 中补充当前行号；不得将本计划中的历史行号当作永久接口。

## 3. 优先级定义

- **P0 — 发布/数据安全门槛：** 在对应能力正式发布或向普通用户承诺前必须关闭。P0 可并行推进，不代表每项都是同一种代码缺陷。
- **P1 — 架构方向性整改：** 在新增大量业务插件或扩大产品范围前优先完成。
- **P2 — 工程治理与长期维护：** 按阶段完成，不能替代 P0 验收。

## 4. 问题清单

### P0：发布、升级与数据恢复门槛

#### P0-01：Worker 候选版本与正式数据代次未完全隔离

- 证据：D。参见 `docs/deployment/WORKER_UPGRADE_AND_RECOVERY.md`、`docs/implementation/ARCH_REMEDIATION_20261016.md` 和 `docs/KNOWN_ISSUES.md`。
- 风险：候选版本在正式数据目录上执行 Schema/数据迁移时，如果升级中断，旧程序可能无法安全回退；禁止危险回退是正确的，但仍需更明确的候选验证和恢复路径。
- 整改：在提交正式代次前，验证候选程序、候选数据/迁移及健康状态；确保迁移失败不污染已确认的正式代次。继续保留升级 Journal、禁止回退新事实和显式恢复策略。
- 验收：覆盖 Schema 迁移失败、进程被杀、系统重启、磁盘满、损坏/缺失快照和候选健康检查超时；恢复后确认已提交事实、原件、审计记录和密钥可用。真实 Windows SCM 安装/升级/卸载/重装需独立实机验收。

#### P0-02：ServiceKey 跨机器灾难恢复尚未闭环

- 证据：D。现有实施记录指出 ServiceKey 仍依赖 LocalMachine DPAPI 与服务身份，独立恢复凭据和跨机恢复尚未完成。
- 风险：仅备份数据库和原件，不能保证在新 Windows 机器/新服务身份下恢复解密能力。
- 整改：设计独立、受控、可离线保管的恢复凭据封装；明确谁可恢复、如何审计、如何轮换及如何撤销。不得通过放宽 SID/身份校验或直接改变 DPAPI 附加熵来“解决”恢复问题。
- 验收：在干净 Windows 环境中，以正式服务身份完成备份恢复、数据库解密、原件校验和任务状态恢复；证明没有依赖旧机器的隐含状态。

#### P0-03：市场监控与税务计算仍有发布门槛未通过

- 证据：D。参见 `docs/implementation/MONITOR_READINESS_20261020.md`、`docs/implementation/PERFORMANCE_P0.md`、`docs/validation/RELEASE_ACCEPTANCE.md` 和 `docs/KNOWN_ISSUES.md`。
- 当前基线记录：24 只 ETF 中 11 只达到 250 个有效交易日覆盖；连续采集验收记录为沪市 1/20、深市 0/20。税务独立金额 Golden Dataset 与真实账户独立签认亦未关闭。以上均为该基线记录，不应被当作永久当前状态。
- 整改：每次实施前重新读取最新验收记录。监控发布必须按具名标的、权威日历、来源原件、缺口/修订、连续采集及预警输入完整性验收；税务发布必须有独立预期值，不能由当前程序输出反向生成黄金答案。
- 验收：达到各专项文档规定的真实数据和独立签认门槛；不能用“服务启动成功”“合成测试通过”或“架构整改完成”替代业务验收。

### P1：必须优先完成的架构收敛

#### P1-01：NationalTeam Core / Jobs / UI 的项目边界与源码所有权不一致

- 证据：S。文件：`src/Plugins/CRS.Plugins.NationalTeam.Core/CRS.Plugins.NationalTeam.Core.csproj`、`src/Plugins/CRS.Plugins.NationalTeam.Jobs/CRS.Plugins.NationalTeam.Jobs.csproj`、`src/Plugins/CRS.Plugins.NationalTeamWatch/CRS.Plugins.NationalTeamWatch.csproj`。
- 观察：Core/Jobs 项目通过跨目录 `Compile Include` 编译位于 NationalTeamWatch 目录中的 Domain/Application/Infrastructure 源码，UI 项目又排除部分相同目录。项目/程序集已经分开，但文件所有权和构建边界仍不清晰。
- 风险：后续开发人员不知道应在哪个项目维护领域规则；项目引用关系不能完全表达源码实际归属；增加业务插件时容易复制、链接或重复编译代码。
- 整改：把领域与应用模型迁入 Core，把后台采集、市场库和来源策略迁入 Jobs，把 WPF 页面和 ViewModel 留在 UI；删除跨项目源码链接，改为清晰的 ProjectReference。共享代码必须有明确归属，禁止用新的共享源码链接掩盖边界。
- 验收：生产项目不再通过跨目录 Compile Include 共享业务实现；依赖图与目录归属一致；全量构建、架构检查、插件打包及现有业务回归通过；数据库 Schema 和业务输出不变。

#### P1-02：桌面插件宿主仍保留旧 Quartz/任务存储实现

- 证据：S。文件：`src/CRS.PluginHost/QuartzTaskScheduler.cs`、`src/CRS.PluginHost/TaskPlanStore.cs`、`src/CRS.PluginHost/PluginRuntime.cs`。当前桌面运行时已采用 Worker 拥有调度的方向。
- 风险：当前不等于两套调度器正在同时运行；真正的问题是旧实现和旧契约仍可被后续代码误用，造成任务所有权倒退。
- 整改：先用代码搜索确认全部生产调用方已迁出，再删除无调用方的旧调度实现/契约。仍有价值的 Cron 编辑或纯模型能力可迁移为不持有执行权的纯工具。
- 验收：生产桌面插件无法创建或执行正式后台计划；所有持久计划和执行历史均由 Worker 管理；旧契约的残留仅允许出现在明确标记的迁移文档或测试夹具中。

#### P1-03：后台查询会话注册依赖任务列表

- 证据：S。文件：`src/CRS.Worker.PluginHost/BackgroundPluginCatalog.cs`，方法 `QueryAsync`（评审基线约第 28–35 行）。
- 观察：查询会话通过已注册的 jobs 列表反向查找，取首个匹配插件的 Session；一个实现查询接口但不声明 Job 的插件可能无法被查询路由找到。
- 风险：插件能力模型被任务清单意外绑架，纯查询、只读研究或不需要定时任务的插件无法自然接入。
- 整改：在 Catalog 中分别注册插件会话、Job、Query 和其他能力；查询路由不得依赖 Job 是否存在。能力注册必须检查重复 ID、缺失实现、生命周期和错误状态。
- 验收：新增一个无 Job、只有 Query 的测试插件可被查询；只有 Job、没有 Query 的插件仍可正常调度；初始化失败只影响对应插件，错误能被诊断。

#### P1-04：MarketRepository 查询路径可能持久化修改证据质量状态

- 证据：S。文件：`src/Plugins/CRS.Plugins.NationalTeamWatch/Infrastructure/MarketRepository.cs`，方法 `ValidateEvidence`、`Evidence`、`Points` 等。
- 观察：证据校验除读取/哈希核对外，在发现异常或恢复原件时还会写入完整性事件、更新质量问题状态；部分查询方法调用该校验逻辑。
- 风险：读取操作可能改变持久状态，增加权限审查、事务一致性和测试复杂度。该观察本身不等于已确认存在权限提升漏洞。
- 整改：拆分纯校验器、完整性状态命令和后台巡检作业。查询应读取已提交的完整性状态；如需要即时复核，应返回校验结果，持久化状态变化走明确的命令/事务路径。
- 验收：普通只读查询在证据正常、损坏和恢复三种夹具下不直接修改持久状态；完整性作业能够记录损坏/恢复事件且幂等；现有原件保全与审计语义不丢失。

#### P1-05：业务对象构造与部分业务决策落在 WPF ViewModel

- 证据：S。文件：`src/CRS.Desktop.Wpf/ViewModels/PerformanceViewModel.cs`，例如 `AddValuation`/估值提交附近（评审基线约第 254–281 行）。
- 观察：ViewModel 直接构造多个绩效领域/应用模型，并决定部分金额、日期、组成项和序列化输入。
- 风险：未来批量导入、自动化任务或其他 UI 入口可能重复实现相同规则。
- 整改：按用例迁移有业务意义的构造和校验至 Application；ViewModel 仅处理表单状态、格式转换和展示错误。不要为了“纯化 UI”重写全部页面。
- 验收：同一用例可通过 Application 测试独立调用；WPF 不再决定领域不变量；现有绩效结果和冻结结果兼容性测试通过。

#### P1-06：双宿主契约和插件业务查询协议的版本边界不清晰

- 证据：S/H。文件：`src/CRS.PluginHost/PackageVerifier.cs`、`src/CRS.Worker.PluginHost/BackgroundPluginCatalog.cs`、`src/CRS.Worker.Abstractions/Contracts.cs`、`src/CRS.Worker.Ipc/Protocol.cs` 及国家队插件 `plugin.json`。
- 观察：桌面契约与后台 HostContract 分别验证；后台查询采用字符串 payload/JSON 并在插件入口通过 Operation 分发。该方式当前可工作，但业务查询 Schema 的独立版本治理需要明确。
- 风险：宿主协议、插件加载契约和 ETF 业务 DTO 演进时容易相互牵制；这属于兼容性设计风险，不是已确认的当前协议故障。
- 整改：宿主 IPC 协议只负责身份、帧、请求 ID、错误与基本兼容；插件业务请求/响应使用各插件自有的版本化 DTO/Schema。明确兼容窗口、拒绝策略和错误码。公共 Abstractions 保持小而稳定。
- 验收：旧/新宿主协议和插件 Schema 的兼容矩阵测试通过；未知版本明确拒绝且不静默降级；IPC 帧大小、取消、超时及错误处理测试通过。

#### P1-07：同进程插件故障会扩大为整个 Worker 的故障域

- 证据：S。文件：`src/CRS.Worker.PluginHost/BackgroundPluginCatalog.cs`、`src/CRS.Worker.Service/Program.cs`。不响应生命周期取消的插件最终可能触发宿主进程终止。
- 风险：一个失控插件可能导致其他插件任务同时中断。当前策略在同进程模型下可以保护宿主存储不被不受控清理破坏，但它不是插件隔离沙箱。
- 整改：保留可信第一方低风险插件同进程运行；先完善超时、诊断和故障状态。只有对高风险/高资源插件确有需求时，另行设计低权限独立 PluginRunner；不得仅靠 AssemblyLoadContext 宣称安全隔离。
- 验收：一个插件初始化/查询/停止失败不污染其他插件的状态；不合作插件触发可诊断的受控退出；独立进程模式如实施，需验证 IPC、身份、数据权限和重启策略。

#### P1-08：投资绩效与税务共享券商事实尚未完全统一

- 证据：S/D。文件：`src/CRS.Application/Imports/BrokerActivityFacts.cs`、`src/CRS.Infrastructure/Performance/IbkrPerformanceAdapter.cs`、`docs/implementation/PERFORMANCE_P0.md`。
- 观察：富途路径已使用共享券商事实模型；IBKR 绩效仍有独立适配路径，相关文档将统一工作列为未完成。
- 风险：同一原始券商活动在税务与绩效模块被不同解析器解释，产生事件分类或来源证据不一致。
- 整改：建立小而稳定的不可变 Broker/Investment Facts；税务与绩效消费同一原始事实，但保留各自投影、成本算法和业务规则。逐步迁移 IBKR，不得一次性重写税务算法。
- 验收：相同原始文件产生相同的共享事实；税务与绩效各自的 Golden Dataset 不回归；转仓、公司行动、费用、股息、现金事件和未知事件均有具名样本。

#### P1-09：跨插件来源预算和过载治理未形成完整公共能力

- 证据：D。参见 `docs/architecture/CURRENT_ARCHITECTURE.md`、`docs/implementation/ARCH_REMEDIATION_20261016.md` 与 `docs/KNOWN_ISSUES.md`。
- 现状：已有插件级有界 FIFO、触发合并、可配置全局并发及部分来源策略；跨插件共享来源预算、长期超载和重试风暴验收仍开放。
- 整改：在 Worker/公共基础设施层提供来源级并发预算、冷却/Retry-After、超时、重试预算和来源健康状态。插件声明来源/资源需求，由宿主实施策略；避免各插件各自限流。
- 验收：两个插件访问同一来源时共享预算；403/429、超时和来源恢复按策略工作；慢插件不长期占用全部 Quartz 名额；长期压力测试不产生无限重试/无界队列。不得承诺任意负载下永不积压。

### P2：工程治理与可维护性

#### P2-01：独立托管 CI 与架构门禁需核实并补齐

- 证据：D/H。现有实施记录指出尚无独立托管 CI；评审基线仓库树未发现 `.github/workflows`。这不排除仓库设置或外部平台可能存在其他 CI。
- 整改：先确认 GitHub 仓库设置与团队实际流水线；若确无自动流水线，新增自动构建、测试、格式/静态分析、架构依赖门禁和发布包验证。
- 验收：每次 PR 自动执行 ReleaseAcceptance 的适用子集；失败可阻止合并；Windows SCM、Named Pipe ACL、DPAPI 和跨机恢复等平台依赖测试仍需专门 Windows 实机流水线/验收，不可由纯单元测试替代。

#### P2-02：统一插件清单、签名与供应链兼容矩阵

- 证据：S/D。桌面与 Worker 分别有清单验证器，当前方案面向可信第一方插件。
- 整改：抽取必要的包身份、路径包含、哈希、契约版本与签名验证规则，减少重复策略；允许两个宿主保留不同的加载生命周期。第三方插件市场不在本次范围内。
- 验收：路径穿越、未信任文件、哈希不匹配、宿主版本不兼容和共享程序集版本冲突均有负例；文档明确“签名/哈希不等于进程沙箱”。

#### P2-03：持续维护架构事实与历史兼容矩阵

- 整改：每次项目依赖、宿主契约、插件 Schema、持久化 Schema 或发行标识变更时，更新当前架构入口与对应兼容矩阵。历史记录保留审查基线和验收证据，避免多个文档同时声称“当前实现”。
- 验收：`CURRENT_ARCHITECTURE.md` 与实际项目引用、启动入口和唯一调度权威一致；已关闭问题链接到测试/提交，未关闭问题明确保留。

## 5. 目标架构与边界

目标结构：

1. **WPF Desktop Shell**：导航、设置、账户交互和插件 UI；不拥有正式后台调度，不直接承载长时间采集。
2. **Domain/Application**：税务、绩效及跨功能用例；业务不依赖 WPF、Quartz 或具体数据库。
3. **Investment Facts / Broker Facts**：小型、不可变、可追溯的共享事实契约；只共享事实，不合并税务和绩效算法。
4. **公共市场业务插件**：国家队 ETF/股票、来源适配与研究能力拥有各自领域规则和数据模型。
5. **Worker Service**：唯一正式后台调度权威；统一任务计划、执行记录、插件能力注册、来源预算、通知和健康状态。
6. **安全数据域**：私人税务/账户保险库与公共市场监控库保持分离，使用各自的数据访问和密钥边界。
7. **验证与发布层**：自动架构门禁、回归、独立 Golden Dataset、数据覆盖验收、恢复演练和发行包签名。

### 明确非目标

- 不改成微服务，不新增 Web API 作为前提。
- 不引入 Redis、RabbitMQ 或分布式数据库来解决单机资源治理。
- 不替换 WPF、Windows Service、Quartz.NET、SQLCipher。
- 不把所有业务模块强行插件化；账户、券商事实、税务与绩效可以是核心业务模块。
- 不把“统一投资事实”理解为合并数据库、密钥、税务成本与绩效成本算法。
- 不在本计划中开放第三方不可信插件市场。
- 不批量重命名持久化标识、服务名、管道名、插件 ID 或密钥保护常量。
- 不修改税务口径、FIFO、汇率口径、ETF 来源口径或预警阈值；任何业务语义变更必须单独立项和独立验收。

## 6. 分阶段执行计划与依赖

P0 发布门槛应并行推进，不因架构清理而延后。以下阶段描述架构整改顺序，不代表可以跳过 P0。

### 阶段 A：低风险架构收敛

任务：P1-01、P1-02、P1-03、P1-04。

顺序：
1. 先新增/确认项目边界和行为回归测试。
2. 迁移 Core/Jobs/UI 源码所有权，删除跨目录编译。
3. 确认旧桌面调度器无生产调用方后删除旧实现。
4. 拆分插件会话与 Job 注册。
5. 将证据校验与持久状态变更分离。

验收门槛：全量构建、架构依赖检查、插件打包、后台任务/IPC/证据审计回归通过；无数据库 Schema 或业务结果变化。

### 阶段 B：领域与协议边界

任务：P1-05、P1-06、P1-08。

依赖：阶段 A 的项目所有权先清晰；事实层先定义契约和黄金样本，再迁移适配器。

验收门槛：业务规则不再由 ViewModel 决定；IPC 与插件业务 DTO 的版本边界明确；IBKR/Futu 共享事实测试通过，税务和绩效独立 Golden Dataset 不回归。

### 阶段 C：Worker 可靠性与资源治理

任务：P1-07、P1-09、P2-02。

依赖：先稳定插件能力注册和公共契约；独立进程隔离必须单独做威胁模型，不作为本阶段默认前提。

验收门槛：插件异常、取消、慢查询、来源限流、重试风暴和服务重启有自动化夹具；跨插件来源预算一致；所有持久任务仍由 Worker 唯一管理。

### 阶段 D：发布与运维闭环

任务：P0-01、P0-02、P0-03、P2-01、P2-03。

验收门槛：候选数据代次与显式恢复流程通过真实 Windows 验收；干净机器可恢复 ServiceKey 和数据；税务金额及监控数据达到专项文档的业务发布标准；CI 与当前架构文档保持一致。

## 7. 每个专项 PR 的必备内容

每个 PR/提交必须包含：

- 任务编号、当前基线 SHA、变更目的和明确的非目标。
- 修改前的复现/测试或当前行为证据。
- 影响的项目、数据表/Schema、IPC/插件契约和持久化标识清单。
- 单元测试、集成测试、架构门禁和需要的 Windows 实机验收结果。
- 兼容/迁移策略、失败处理、回滚边界和日志/诊断变化。
- 更新本文件中对应任务的状态：Open / In Progress / Blocked / Verified。
- 若发现原结论已经在后续提交修复，必须链接对应提交与测试，并标记为“已由后续提交关闭”，不得重复实现。

禁止用以下说法关闭问题：“编译通过”“代码看起来更干净”“新增了接口”“单元测试通过”——除非该问题的验收标准本身只要求这些内容。
