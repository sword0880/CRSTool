后续：R01～R04已实施候选整改并通过专项与隔离联动验证，见[四项整改记录](../implementation/ARCH_OPTIMIZATION_20261023.md)。下文保留评审时事实和证据，不据此推定正式服务已更新。

评审基线：`b4a4b63ad86bf0d0bc3336c19011d5c48e2fdff4` 工作区。评审时已有两份国家队分组并发相关文档变更，未覆盖或修改。本文仅评审，不实施业务整改，不操作已安装 Worker、密钥或真实数据库。

## 总体判断

现有模块化单体加独立 Worker 的方向适合本地投资与税务工具。Domain/Application/Infrastructure 的依赖方向、WPF 展示边界、个人保险库与市场库分离、Worker 唯一调度、命令持久幂等、金融证据失败关闭，都值得保留。当前主要问题集中在运行边界和交付闭环；继续增加项目、接口或服务数量不会自动解决。

本轮发现分为已确认的源码行为、由源码推导的规模风险，以及既有但尚未接线的发布缺口。未重新检查本机正式服务，文中不推定工作区能力已部署。优先级中 P0 表示发布阻断，P1 表示应优先整改，P2 表示后续结构优化，不表示已经发生数据丢失或线上事故。

## R01：解析器承担了另一个业务用例的提交

证据：

- `src/CRS.Application/Workflows/DesktopWorkflow.cs:84` 开始税务计算，`:88` 才保存税务结果。
- `src/CRS.Infrastructure/Composition/DesktopOperations.cs:20` 在创建计算器时注入同步绩效回调，`:24` 调用 `ImportSharedPerformance`。
- `src/CRS.Infrastructure/Brokers/Futu/FutuImporter.cs:37` 在逐份交易文件读取过程中调用回调；后面才检查收入主表是否存在及有效。
- `src/CRS.Infrastructure/Brokers/IBKR/IbkrXmlParser.cs:71` 同样逐份原件触发回调。
- `src/CRS.Infrastructure/Storage/SqlCipher/SqlCipherVaultBackend.Performance.cs:7` 打开绩效导入路径；`src/CRS.Infrastructure/Performance/PerformanceStore.cs:126` 与 `:148` 建立并提交独立事务。

具体场景：选择一份可成功导入绩效的富途交易工作簿，但没有收入主表。交易文件的绩效写入可能已经提交，随后税务解析抛错，税务历史不保存。多文件后续解析失败、后续计算失败或取消也有类似边界。这里没有证据表明金融金额计算错误；问题是用户操作的失败语义与实际写入范围不一致，Application 也不能从解析器接口看到这个副作用。

建议：让解析器只产生不可变来源与投影结果，由 Application 显式编排税务、绩效两个用例。先明确产品语义：若应全部成功，使用同一存储事务/工作单元；若允许绩效独立成功，则持久保存导入批次与每个子步骤状态，并把部分成功、重试和去重明确交给用户。不要仅将回调改名或搬到另一个基础设施类。

验收：覆盖首文件成功后第二文件失败、缺少收入主表、计算阶段失败、保存失败和中途取消；逐项检查税务与绩效实际落库状态、重试幂等和界面结果是否符合选定语义。

## R02：查询隔离只完成了宿主准入，未完成插件内部读写隔离

证据：

- `src/Plugins/CRS.Plugins.NationalTeam.Jobs/Application/EtfWorkspace.cs:24` 的 `RunAsync` 在同一 `SemaphoreSlim` 内执行查询与写入。
- `src/Plugins/CRS.Plugins.NationalTeam.Jobs/Infrastructure/EtfDashboardRepository.cs:10` 在读事务中核验原件，再读取概览、历史、成交统计。
- `src/Plugins/CRS.Plugins.NationalTeam.Jobs/Infrastructure/MarketRepository.cs:301` 执行原件批量核验；`:365` 起对每只证券读取点序列和日历并计算概览。
- `src/Plugins/CRS.Plugins.NationalTeam.Jobs/NationalTeamBackgroundEntry.cs:233` 的查询先读取业务结果并序列化为完整数组，`:319` 才检查 10000 行/2 Mi 字符和全会话 8 个快照上限；`:331` 起的分页仅对这个数组切片。

影响：网络等待已不占数据库门槛，原件核验也已有取消与四路并行，这些改进有效。但一次重查询仍会延后同会话采集提交、审核和预警数据库操作；提高 Quartz/分组并发不能消除这个内部串行点。十行分页不等于十行数据库读取，结果超限也不能保护前面的数据库读取、核验和序列化成本。快照额度属于整个会话，多客户端还会相互占用。

建议分两步做：先下推日期、证券、游标和行数边界，使用 `limit + 1` 等方式在读取阶段判定后续页；再建立独立只读连接/一致性读模型，缩短写事务和串行门槛。原件核验可在门槛外处理已冻结的证据引用，返回前重新核对修订/完整性状态，防止核验与返回之间的数据竞态。概览可建立有版本的派生投影并批量读点序列、复用同市场日历。不能通过无条件缓存“已验证”或跳过原件核验来换速度。

验收：在不断采集、原件损坏/恢复、查询取消和多客户端同时存在时，测查询 P95/P99、写入等待、锁持有时间、首屏延迟与峰值内存；核对失败关闭及事实修订一致性。规模采用明确的历史年数、证券数和原件字节数，不能仅用空库测试。

## R03：插件是扩展边界，还不是独立故障域

证据：`src/CRS.Worker.Service/Program.cs:83` 创建进程内 `BackgroundPluginCatalog`，`:85` 的不合作回调直接 `Environment.Exit(2)`；`:125` 停止超时也终止进程。该启动入口没有启动 PluginRunner。

影响：一个可信插件的死锁、失控取消或原生崩溃仍可中断其他插件、查询和通知。ALC、哈希、派生密钥解决不同问题，不能据此承诺故障隔离或第三方安全沙箱。现在的终止策略有保护存储生命周期的合理性，不应简单删掉。

建议：沿现有 `WORKER_PLUGIN_PROCESS_ISOLATION.md`，先完成 Heartbeat 的 Worker→Runner 监督纵向链路，再逐插件迁移。Quartz、持久命令、执行历史和来源预算继续由 Worker 拥有；子进程具有资源预算、进程树清理、重启退避及结果未知语义。故障隔离与 OS 权限隔离分别验收，暂不扩大第三方插件承诺。

验收：对 Start/Query/Execute/Stop 注入不合作、崩溃与进程强杀，其他插件继续查询和执行；旧 Runner 未确认退出前禁止启动第二个写库实例；不得对结果未知的业务命令自动换 ID 重放。

## R04：整树权限巡检将容量问题升级为全服务故障

证据：

- `src/CRS.Worker.Service/Program.cs:101`、`:105` 每 30 秒同步检查完整数据树，之后才执行协调循环。
- `src/CRS.Worker.Service/Security/StorageSecurity.cs:8` 将目录项上限固定为 100000，`:54` 超过即抛出安全异常。
- `tools/background/WorkerMaintenance.psm1:110` 将升级快照保存在同一数据根的 `maintenance/<id>/snapshot`，原件存证则按内容哈希形成独立 `.raw` 文件。

影响：扫描成本随整树增长，历史快照也在范围内；即便每个文件 ACL 正确，正常增长到上限仍会进入停止路径。服务重启后启动检查再次失败，无法通过重启自行恢复。这是确定的容量边界，不代表当前已安装目录已接近该数量；本轮未统计真实私有数据。

建议：制定证据、快照和日志的容量预算、预警与保留政策，将安全异常与容量耗尽分类。对增长目录按受控分区检查，设计有界、可取消且不会长期阻塞协调循环的巡检；变更检测只是辅助，仍保留定期全量验证。维护快照按明确生命周期归档，并保持归档权限与恢复完整性核验。不要直接删除仍被事实或审计引用的原件，也不要取消 ACL 检查。

验收：模拟大目录、多代快照、达到阈值、真实 ACL 漂移及取消，验证能够提前报告容量风险，不因合法历史增长突然全服务不可用；同时保留越权访问失败关闭。

## R05：检查通过尚不能代表主要业务路径都回归过

证据：

- `.github/workflows/wpf-ui-design-checks.yml` 对 PR 全量构建并执行架构、部分 Worker/插件/UI 专项，但没有运行 Domain/Application/Infrastructure/Security/Verification 的完整默认回归。
- `tests/CRS.Tests.Domain/Program.cs:2` 遇到 `--performance-architecture` 会检查后直接返回；架构门禁调用该参数，不会顺带运行 FIFO、税务及完整绩效回归。
- `tests/Run-ReleaseAcceptance.ps1` 的回归循环仅列 Domain/Application/Security/Infrastructure/Wpf/Verification，没有把 Background/WorkerEtf/NationalTeamWatch/PluginRecovery 等作为统一整体验收集合。其余工作流提供部分专项补充，但不构成统一覆盖清单。

影响：修改金融规则可能只得到编译与展示专项的绿色结果；发布脚本也可能遗漏整套 Worker/插件回归。现有测试是可执行程序，构建它们不会自动运行测试。

建议：建立唯一验证目录，逐项列出入口、适用范围、是否必跑、数据性质和最终证据。普通 PR 必跑无真实数据的核心金额/应用/安全回归；Worker 与插件变更执行对应完整集合；发布候选追加安装、恢复、兼容与容量验收。可继续复用现有可执行测试，无需为了统一入口立即改写整个测试框架。报告记录源码提交、包摘要及跳过原因；独立金额签认继续单列，不由程序自回归代替。

验收：故意引入一处合成 FIFO 或应用事务回归，确认 PR 失败；引入 Worker/ETF 回归，确认候选发布失败；检查跳过项目不会显示为成功。

## R06：接口形式解耦了类型，但能力语义仍然过宽

续项：市场仓储默认实现已移除，按用例拆分端口并在正式启动核验必需能力；R07 年度边界已修正。
R08 仅推进内部持久授权，发布门槛仍 Open。当前状态及验收见[续项记录](../implementation/ARCH_FOLLOWUP_20261023.md)，下文保留评审时证据。

证据：`src/Plugins/CRS.Plugins.NationalTeam.Core/Application/Ports.cs:11` 的 `IMarketRepository` 同时包含采集、日历、股票报告、预警、通知 Outbox 和配置；大量方法默认抛 `NotSupportedException`，部分方法默认返回空集合或 null。`src/CRS.Infrastructure/Storage/IVaultStorageBackend.cs` 同时提供仓储、绩效用例工厂、会话保护委托和跨模块导入。

影响：新增适配器可以编译通过，直到业务运行时才发现能力缺失；默认空集合还需要调用方额外区分“没有数据”和“不支持查询”。备份、会话和事务一致性也不能仅靠一个提供方名称得到证明。当前没有证据表明内置 SQLCipher 适配器正走默认空实现，不将它描述为当前数据被漏读。

建议：按已有用例拆出较小的查询、采集写入、预警评价及投递端口，显式声明可选能力，启动时核验所需能力。生产契约必需方法不提供假空默认实现，测试夹具通过专用适配器迁移。继续只维护当前确有需求的 SQLCipher 提供方；第二数据库应在实际需求出现后，连同加密、事务、备份和迁移一致性测试一起实施。

## R07：北京时间策略尚未覆盖业务年度边界

证据：`src/CRS.Application/TaxCalculation/CalculationService.cs:81` 使用 `clock.GetLocalNow().Year` 判断是否为临时年度；`src/CRS.Time/BeijingClock.cs` 已提供 `Read(TimeProvider)`，Application 也已引用 CRS.Time。

影响：北京已跨年而主机时区尚未跨年时，同一年份可能得到不同的 Provisional 判定，影响结果状态。结果重放保存该标记有助于稳定历史，但新计算仍受机器配置影响。这是业务时钟边界问题，不是界面日期格式问题。

建议：用注入时钟的 UTC 时间显式转换到业务北京时间，再取得年度；保持重放沿用冻结语义。补同一 UTC 时刻、不同主机时区，以及北京时间跨年前后的边界验证。该修改涉及结果状态，应单独评审，不混入普通目录整理。

## R08：跨机恢复仍是发布阻断，不能由加密备份替代

证据：`src/CRS.Worker.Service/Security/ServiceKey.cs` 生产路径仍校验 SID 并调用 LocalMachine DPAPI；`RecoveryExportSession.cs:6` 明确仍为阶段 2a，未注册生产 IPC/CLI。Program、运行时及协议入口没有完整恢复导出与目标激活链路。

影响：机器丢失或无法访问原 DPAPI 环境时，单独拷贝任务库、市场库与 DPAPI 文件不足以保证恢复。内部恢复封装和授权状态机是进展，但不是操作人员可执行的灾备方案。

建议：继续完成停写快照、一次性授权导出、独立恢复凭据、目标重封装、只读验库、显式激活和审计链路。以干净机器演练关闭 ARCH-005/P0-02，不能仅凭内部组件测试关闭。此项复核的是已有缺口，不撤销已有机器内升级事务的改进。

## 推荐整改顺序

1. 先补 R05 的统一验证入口，再明确并修复 R01 的跨用例提交语义；两者范围可控，直接提高后续整改可信度。
2. 紧接 R02 的有界读取与 R04 的增长治理，先做可度量的改进，再决定是否引入概览投影。
3. R08 按安全阶段推进至干净机器恢复验收；它继续阻断公开发布。
4. R03 先完成最小插件监督纵向链路，再迁移高资源插件；R06 随这些用例拆分逐步收敛。
5. R07 单独修正并验证业务状态，不改税务/FIFO/汇率金额规则。独立税务黄金样本仍按既定顺序处理，不能用本轮架构评审代替。

不建议当前改成微服务、增加消息中间件、拆出远程数据库或建立通用插件市场。现有独立 Worker 已提供必要的后台生命周期，优先把运行边界、容量、恢复和验证做实。
