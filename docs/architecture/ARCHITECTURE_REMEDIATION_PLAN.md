## 2. 评审基线与证据规则

### 2.1 基线范围

本轮评审基于指定提交的项目结构、关键项目文件、后台插件宿主、IPC、市场数据仓储、绩效 ViewModel、升级恢复文档和当前问题清单。它不是逐文件全量审计；本轮没有执行全量构建、动态故障注入、真实 Windows SCM/DPAPI 测试或生产发行验收。

### 2.2 证据标签

所有专项任务必须使用以下标签，避免把风险推断写成已复现缺陷：

- **S — 源码确认**：代码结构或调用路径已定位；不自动等于已在生产复现。
- **D — 文档确认**：现有设计/实施/验收文档明确记录该限制或未关闭事项。
- **V — 待验证**：需要调用链、运行时、压力、故障注入或真实环境测试才能确认影响范围。
- **R — 建议/目标**：架构优化建议，不表示现状必然错误。

关闭任务时必须记录：改动提交、测试命令及结果、关键日志/截图/测试夹具、未覆盖范围、回滚办法。仅有“构建通过”不能替代业务正确性、真实服务环境和灾备验收。

## 3. 问题分级与整改清单

优先级含义：
- **P0 — 发布或数据安全门槛**：在对应产品能力正式发布前，必须有明确证据证明安全、正确或可恢复；不表示已确认存在可利用的安全漏洞。
- **P1 — 架构边界/可靠性整改**：扩大插件范围、依赖长期无人值守运行或增加新业务前优先处理。
- **P2 — 工程治理与复杂度控制**：在扩大团队/功能或正式发行前完成，避免债务持续增长。

## 4. 目标架构与边界

### 4.1 目标职责

- **WPF Desktop Shell**：界面、用户交互、表单和展示；通过 Application 用例或 IPC 与业务/Worker 交互。
- **个人投资领域**：账户、证券/交易事实、税务、绩效和组合。税务与绩效共享可追溯事实，但保持独立计算模型与验收基准。
- **公共市场领域**：证券与 ETF 参考数据、国家队公开数据、来源质量、预警规则与事件证据。
- **Shared Contracts / Investment Facts**：只放跨模块真正稳定的身份、事实、证据引用和版本化 DTO，不承载所有业务规则。
- **Worker Platform**：唯一正式后台调度权威、IPC、插件能力注册、来源预算、健康监控、加密任务存储与升级恢复。
- **Infrastructure**：具体数据库、网络源、文件和系统集成。依赖方向必须可被自动化门禁验证。

### 4.2 明确非目标

1. 不推翻 WPF + Windows Service + Quartz.NET 的整体方案。
2. 当前不引入微服务、Redis、RabbitMQ 或外部任务队列。
3. 不把所有业务规则塞进公共 Contracts，也不为追求“统一”而合并税务与绩效算法。
4. 不把 AssemblyLoadContext 视作安全沙箱。
5. 不因品牌“小财牛”而批量重命名持久化标识、密钥保护常量或 Windows 运行身份。
6. 不把代码审阅结论包装为已完成构建、实机测试或发布批准。
7. 不在本专项中改动与问题无关的业务计算、税务口径、投资规则或用户数据。

## 5. 分阶段执行顺序

### 阶段 A：先锁定发布门槛和证据

任务：ARCH-101、102、103、104。

- 在证据不足时保持“未通过/未关闭”，不以其他功能测试替代。

### 阶段 B：收敛模块所有权和读写边界

任务：ARCH-201、202、203、204、205。

推荐顺序：
1. 修正 Core/Jobs/UI 的源码所有权与项目依赖。

每一步单独提交，先补回归测试，再实施最小改动；避免一次性跨多个模块大重构。

### 阶段 C：稳定插件与跨进程契约

### 阶段 D：统一投资事实与来源治理

- 先从一个来源和一组插件建立端到端验收，再扩展，不进行全仓数据模型推倒重来。

## 7. 风险与迁移策略

- **数据风险**：任何 Schema、事实模型或迁移修改都先备份并在副本测试；不通过自动降级或旧版本回写来“修复”新数据。
- **密钥风险**：不得变更现有 DPAPI 附加熵、密钥封装常量或服务身份而没有专门迁移/恢复设计；禁止明文密钥方案。
- **兼容风险**：IPC Host 协议、插件业务 DTO、持久化 Schema 使用独立版本号。无法兼容时明确拒绝，不静默猜测。
- **运行风险**：取消令牌不等于线程已停止；不合作插件不得在未确认终止的情况下被假设为已安全卸载。
- **金融结论风险**：行情/ETF 来源完整性不足时不得生成“已验证”预警；税务/绩效结果不能用自身输出作为唯一正确性证据。
- **范围风险**：每个任务单独分支/提交，保持改动可审阅；不把品牌重命名、UI 美化和业务算法重写混入架构整改。
- **回滚原则**：代码可回滚不代表数据可回滚。对已写入的新事实和 Schema 变更必须定义恢复路径；若无法安全回退，则采用前向修复与明确的维护模式。
