## 3. 问题、影响与整改要求（首次复审的整改前证据）

### AR-01 / P0：年度聚合仍然相加账户税额

证据：[AnnualTaxAggregationService.cs](../src/CRS.Application/TaxCalculation/AnnualTaxAggregationService.cs)，对 GainTax、ForeignCredit、SupplementTax 逐项 Sum；[TaxEngine.cs](../src/CRS.Domain/TaxRules/TaxEngine.cs) 的年度算法则先汇总收益，再对正净额计算税。

例：账户 A 已知收益 +100、账户 B 已知收益 -100，无其他所得。按现有年度算法总收益为 0，资本收益税为 0；当前聚合把账户 A 的 20 与账户 B 的 0 相加为 20。同样，逐账户先限额抵免后相加，与年度统一限额可能不同。

整改：账户结果输出可聚合的收入、收益、税款事实；AnnualTaxAggregationService 汇总事实后只运行一次选定年度规则。明确纳税人/账户所有权选择、券商身份、规则版本。不得在缺少原始税款事实时通过反推 ForeignCredit 恢复预扣税。验收新增正负账户抵销、抵免限额和多账户舍入；AGG-001 当前只验证状态，不能验收金额。

附带问题：同年度同币种 Rates 分组后直接取 First，没有拒绝不同来源、数值或规则版本；账户仅以字符串查重，空账户集合可绕过范围校验。聚合前必须校验账户集合非空、归属明确、身份包含券商、父运行可追溯，以及所有参与结果使用兼容的汇率/规则。

### AR-02 / P0：使用结转的快照重放丢失期初来源语义

证据：[CalculationService.cs](../src/CRS.Application/TaxCalculation/CalculationService.cs)。原计算将 carry 的 LOT/余差加入输入，期初确认通过 `carry is not null`；快照没有独立期初来源类型。Replay 用 `carry=null`、`openingXml=null` 重跑，且来源集合没有对应 Opening 报告。

在“C# 上年结转 + 未勾选期初零持仓”的正常输入下，原计算可确认期初，重放却新增 OPENING_UNCONFIRMED，使状态和结转资格变化。即使金额一致，也不能称为同一运行的复算。

整改：快照增加 OpeningSourceKind、结转原始摘要/版本/来源运行编号和按账户确认结果；重放恢复同一输入语义。比较 Summary、所有 Match、LOT、余差、问题码、四维状态及输出摘要；差异产生报告，不能只比较输入摘要。新增 REPLAY-CARRY 与数据库保存/加载后重放测试。

### AR-03 / P0：重放没有冻结执行版本，缺汇率时回退当前配置

证据：[CalculationService.cs](../src/CRS.Application/TaxCalculation/CalculationService.cs)：Rate 使用 `rateSnapshot?.FirstOrDefault(...) ?? rates.Get(...)`；Replay 仅检查 schema，没有执行规则/算法/导入器兼容检查。Provisional 依赖 DateTime.Today；新 SnapshotJson 写当前配置指纹。末尾比较 CanonicalInputDigest，而该 JSON 本身就是原样传回，无法证明输出一致。

整改：重放必需汇率缺失直接报 ReplayUnavailable；快照冻结年度、时点政策、汇率和规则版本；配置指纹引用历史值；新增 ParentCalculationId、ResultDigest 和 ReplayVerificationState。未知版本明确拒绝或经已测试迁移后生成新运行，不静默执行当前规则。业务重算与历史复算是两个明确用例。

### AR-04 / P0：同秒排序与快照排序不一致，可能改变 FIFO

证据：[FifoEngine.cs](../src/CRS.Domain/FIFO/FifoEngine.cs) 排序为 Time、Row；快照 trades 排序为账户、证券、Time、Id。Row 是文件内序号，跨文件可重复。相同证券同秒同 Row 的两笔不同成本买入，原运行以传入顺序决定先后；快照保存后可能按 Id 重新排列，重放选择另一成本。

整改：规范化层定义统一排序契约，保留原始时间、时间精度、原始 ID、源文件哈希和区段序号；原计算和重放使用同一稳定顺序。稳定顺序不能冒充真实先后，无法证明且会影响成本的同秒记录必须复核。验收文件交换顺序、重叠文件、同秒两批成本和同秒买卖。

### AR-05 / P0（历史兼容条件）：含费成本变更仍使用结转 Version=1

证据：[CarryFiles.cs](../src/CRS.Infrastructure/Persistence/CarryFiles.cs) 只接受/生成版本 1；[FifoEngine.cs](../src/CRS.Domain/FIFO/FifoEngine.cs) 现在将 CostDelta 作为含费总成本余差。此前 C# 成本账分别维护本金与买费余差，两者的税额语义不同。旧文件还缺少新模型字段；对反序列化后模型重新序列化计算哈希可能导致旧有效文件被拒绝。

风险：若已有旧版结转，同名 Version=1 不能证明兼容；拒绝旧文件与静默采用新余差含义都应明确处理。

整改：盘点已生成的旧文件；按原始版本 DTO 校验摘要，再显式转换。新格式提升 schema/version，记录算法、成本模式和余差含义。没有旧样本前声明旧版未验收，不承诺兼容。新增旧文件 golden fixture、旧/新一致性和篡改测试。

### AR-06 / P0：抵免证据缺口没有进入结果门槛

证据：[TaxEngine.cs](../src/CRS.Domain/TaxRules/TaxEngine.cs) 按币种汇总预扣税；[CalculationService.cs](../src/CRS.Application/TaxCalculation/CalculationService.cs) 预计补税门槛只检查问题、完整性、对账、临时和汇率来源。模型没有 CreditEligibilityState，未生成 CREDIT_EVIDENCE_MISSING。

来源地/所得项目对应关系尚未核验时，只要其他检查通过，仍可能输出非空抵免后预计补税，与 V1.1 §9.4/§10.3 的设计门槛冲突。该判断是产品证据规则，不是新增税务法规判断。

整改：预扣税事实与审核可抵免额分离；先引入 Unconfirmed/Confirmed/NotApplicable 和证据链接。关系未确认时允许显示预扣税及暂算分项，年度抵免后确定估计保持 null。业务签认后再升级规则。

### AR-07 / P1：模型状态与展示存在多套口径

证据：[Models.cs](../src/CRS.Application/TaxCalculation/CalculationResult.cs) 同时保存 Summary.EstimatedTopUpCny 和 Result.EstimatedTopUpCny；Complete 未直接校验 DataCompleteness/UsageLabel。聚合读取 Result 门槛、金额却取 Summary；两处不一致时可能产生非空零估计。UI 反射展示 SupplementTax，Excel 也同时列原始公式补税和年度预计补税。

整改：实现独立 ResultStatusPolicy，统一预计补税唯一来源；输出已核算部分、暂算和未知范围的专用 ViewModel/Report DTO。不完整年度不以醒目的全年总税额呈现部分计算值。NotVerifiable 与 Differences 分开；缺汇率可导出原币诊断；硬导入错误形成诊断，避免 Blocked 枚举只有形式。

### AR-08 / P1：来源哈希与实际计算可能来自两次不同读取

证据：Parser 在 ReadBytes 后为原始字节计算 SourceReport.Sha256；CalculationService 构建 fileRefs 再 File.ReadAllBytes。文件在两个阶段之间变化时，来源哈希与快照引用会不一致。

整改：一次受限读取形成不可变 ImportFile 描述和字节/解析输入，计算与摘要共用它；去掉二次读取。SourceRef 使用哈希+区段+序号+原始 ID，跨文件同名仍可追溯。相同文件重命名是否可接受由契约明确。默认恢复模式也要记录结转文件引用，当前原始文件校验只覆盖活动/期初 XML。

### AR-09 / P1：规范化快照还不是严格的 canonical 契约

证据：当前序列化为匿名对象，decimal 是 JSON 数字，排序使用默认字符串比较；输入摘要不绑定 Rates、Year、算法和确认策略的整个运行上下文。Replay 的集合默认空值可能掩盖缺字段，且无严格数据结构上限/必填完整性检查。

整改：版本化 Snapshot DTO 固定 UTF-8、字段次序、Ordinal 排序、十进制文本和 null 语义；摘要覆盖完整运行输入上下文；反序列化后执行范围、唯一性和模型校验。哈希提供一致性检测，不提供真实性认证。不要为了合规表述强行把精确 decimal 当成浮点：目前 .NET serializer 直接处理 decimal，主要缺口是跨版本 canonical 规则与完整上下文绑定。

### AR-10 / P1：历史记录版本、可变性和性能没有闭环

证据：[LocalStore.cs](../src/CRS.Infrastructure/Persistence/LocalStore.cs) 使用 user_version=1，将 CalculationResult 整体存 JSON；[Models.cs](../src/CRS.Application/TaxCalculation/CalculationResult.cs) 集合可变、CostLot 可变、SnapshotId/SnapshotJson 可改。新增字段默认值可能改变旧运行加载后的 Complete，而历史索引的 complete 保留旧值。

整改：持久化 DTO 与领域/界面模型分离，增加 result schema、父运行、算法版本及迁移验收；历史状态不按当前默认值重解释。用不可变结果集合或保存时深复制保证运行快照稳定。数据库备份/恢复和版本升级应有测试；需要跨库交换金额时采用固定十进制文本，不把 JSON 本身等同 SQLite REAL。

### AR-11 / P1：桌面端功能与 API 完成度不相同

首次复审证据来自已删除的 MainForm：当时历史窗口只有 Load/Display，没有 Replay/VerifyOriginalFiles/年度聚合入口；保存及导出曾在 UI 线程，表格成本名称也存在问题。当前 WPF 通过 DesktopWorkflow 后台保存和导出；历史页仍只恢复冻结结果，复算及年度聚合入口仍待接入。原问题不应整体视为已关闭。

整改：P0 关闭后再加历史“校验原件复算/快照复算”按钮、父运行展示和账户所有权选择。数据库保存和 NPOI 导出进入受控后台，支持取消/临时文件完成后提交；中文显示四维状态及“含费总成本/费用披露”。WPF 控件布局放 XAML，业务交互放 ViewModel；保存／导出的取消与原子提交仍需专门验收。

### AR-12 / P1：测试名字、规范编号和真实验收证据存在偏差

证据：Program.cs 的 REPLAY-002 是简单快照重放，V1.1 §16.2 同名编号却指“只有哈希无法恢复”；AGG-001 只验状态。现有取消测试针对 Flex；没有计算取消、过期结果、结转重放、版本不兼容及聚合金额测试。

整改：建立稳定测试编号映射；已有规范 ID 不复用为相反场景。把所有 P0 反例作为验收集，真实样本采用受控本地数据并记录年份、来源摘要、已核对分项、未解项及执行版本；不要将原始账户/令牌写入开发文档。测试数量与迁移完成度分别记录。
